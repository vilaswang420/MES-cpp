## AuthForge 集成决策（MVP 前置结论）

- **MVP 采用"自研薄层 + 部分借鉴"**：认证（账密+验证码+JWT+黑名单）按设计文档第 5 章自研（约 1.5 人周）；可选借鉴 AuthForge identity 库的密码哈希/MFA 实现。
- **理由**：① `data_scope` 5 档 + 递归部门 CTE + 多角色取最宽合并（文档第 5.4 节）是 MES 特有权责模型，任何通用 OAuth2 服务器不覆盖，必须自研留在 HMS 侧；② 嵌入式 SDK 会形成 AuthForge ORM 用户模型与 `sys_users`（含 dept_id/employee_no）双用户主数据，双写漂移风险高；③ MVP 无 SSO/OIDC 外部需求，独立授权服务徒增一跳网络与一个运维单元。
- **职责划分（若 M3 后引入）**：AuthForge 负责认证协议层（OAuth2/OIDC 签发、MFA/WebAuthn、IdP 联邦）；HMS 作为 OIDC RP，RBAC 表继续负责授权与数据权限层，两库以 `username/employee_no` 映射。
- **S0 阶段 3 天限时 spike 验证**（`find_package` 构建兼容性、identity 库可否单独抽出、schema 隔离），产出 Go/No-Go ADR；不阻塞主线。

## 阶段 S0：预研 Spike（第 1 周，先行且限时）

1. **S0.1 基础设施打通**（`spike/drogon-infra-poc/`）：Drogon + PG16 读写 + Redis pub/sub + rabbitmq-c 收发全链路；锁定各库版本清单。
2. **S0.2 定制 PG 镜像**（`deploy/postgres/Dockerfile`）：postgres:16 + pg_partman + pg_cron；验证 `partman.create_parent`、`cron.schedule`、审计表跨分区写入（设计文档明确：分区缺失将导致 INSERT 报 "no partition of relation"）。
3. **S0.3 AuthForge 验证**（`spike/authforge-poc/`，限时 3 天）：验证构建兼容性与 schema 隔离；产出 `docs/adr/0001-authforge-integration.md`。
- **DoD**：`compose up` 后"HTTP→PG→Redis→MQ→消费→回写 PG"全链路跑通；ADR 0001 定稿。

## 阶段 M0：工程骨架与 CI（第 2 周）

4. 按上图建立 monorepo 骨架；四个服务各交付 `/healthz`。
5. **迁移管理**：golang-migrate，脚本拆分 `001_auth_tables`（A 域 8 表 + mq_outbox + sys_configs，含 sys_audit_logs 分区与 partman 注册）→ `002_seed`（超管 + 7 默认角色权限矩阵）→ `003_prod_tables`（9 表）→ 后续 `004_iot / 005_qc / 006_integ`；down 仅 dev 用，生产只进不退（expand/contract 规范写入 CONTRIBUTING）。
6. **开发环境** `deploy/compose/docker-compose.dev.yml`：定制 PG 镜像、Redis 7 单实例（禁 cluster-enabled）、RabbitMQ 3.13-management。
7. **后端横切设施**（可维护性地基）：
   - `src/common/ApiResponse.hh` + `ApiException`：统一响应 `{code,message,data,timestamp,trace_id}`（4.1 节），时间一律 UTC ISO8601 带 Z；
   - `registerHandlingErrorAdvice` 全局错误拦截（禁止业务手拼错误 JSON）；
   - `TraceMiddleware`（trace_id 注入日志 MDC 与响应）；JSON 行日志规范；
   - **代码风格约定**：Service 层用 Drogon 协程写事务逻辑，回调只留底层插件（避免报工事务式多层回调嵌套）。
8. **CI 门禁**（`.github/workflows/ci.yml`）：backend 编译+单测+clang-format；web/dashboard build+lint；migrate up+down 往返测试（含跨分区插入用例）；**fail-closed 权限映射完整性检查**（扫描全部 Controller 路由，未注册权限映射则构建失败）。
- **DoD**：`git clone → compose up → migrate up → 四服务 healthz 200` 一条命令完成，CI 全绿。

## 阶段 M1：MVP — A 域 + B 域（第 3–8 周）

### A 域：用户权限 + 系统管理（3–5 周）
9. `AuthController/AuthService`：login/captcha/refresh/logout/profile/password（4.2 节 6 接口）；bcrypt + JWT（payload 含合成后 data_scope/custom_dept_ids），refresh_token 存 Redis `jwt:blacklist` 黑名单。
10. `JwtMiddleware + RbacMiddleware + AuditMiddleware`：严格按 5.3 节实现，**fail-closed**；权限-路由映射集中注册于 `src/middlewares/perm_routes.cc`；审计异步批量写分区表（失败只记日志不阻断）。
11. 用户/角色/部门/权限树/数据范围 CRUD（4.3–4.5、4.11 节）；`RbacService` 实现多角色 data_scope 取最宽合并；`utils/DataScopeFilter.hh` 实现 5 档 SQL 条件注入（含递归 CTE）；权限缓存 `perm:user:{userId}` 主动失效。
12. `hms-web` 骨架：登录页、布局 + 按 permissions 动态菜单、用户/角色/部门/权限/审计 5 组管理页；统一 `request.ts`（code≠200 处理、401 跳登录、trace_id 上报）。

### B 域：生产管理（5–8 周）
13. 主数据 CRUD：产品/产线/工位/工艺路线/工艺步骤（迁移 003）。
14. `WorkOrderController/Service`：工单 8 态状态机（0–7）**表驱动**建模（拒绝散落 if-else），16 个接口（4.6 节）。
15. **报工事务**（7.5 节范式）：工序行级更新 → 工单汇总 → 完工时事务内写 `mq_outbox` → COMMIT 后投递；投递器 = Drogon 定时任务 + `pg_try_advisory_lock`（MVP 不引 Redis 分布式锁）；停采指令消费端先日志占位。
16. 生产计划 + `prod_plan_work_orders` 关联维护；`hms-web` 工单列表/详情（工序 Tab）/报工弹窗/计划页。

### M1 出口标准（硬门禁）
- E2E 脚本 `tests/e2e/m1_flow.sh`：登录→建工艺→建单→下达→报工×2→自动完工→outbox 标记已投递，全程无人工改库；
- 权限反例：operator 访问 `system:user:list` 返回 403；data_scope=1 用户查不到他人创建的工单；审计可分页查询；
- k6 基线（校准版）：500 VU 混合场景（登录 10%/查询 70%/报工 20%）10 分钟 P95 < 300ms、错误率 < 0.5%。

## 阶段 M2：完善 — IoT / 质量 / 看板 / 集成（第 9–14 周）

17. **MQ 拓扑先行**：按 `deploy/mq/topology.json` 声明 exchange/queue/DLX/`iot.retry.queue`（TTL）；消费重试计数走消息头 `x-retry-count`（7.3 节修复后契约）。
18. **hms-iot 采集服务**：Modbus TCP 首发协议；并发模型 = epoll 事件循环 + 协议 worker 线程池；采集线程就地缩放/校验，发布线程**批量 publish**（≥100 条或 100ms 窗口 + publisher confirms）；严格遵守 contracts/iot-message.schema.json（含 version 字段）。**先用模拟器脚本发 MQ**，后端开发不被硬件阻塞。
19. **消费入库链路**：`DataIngestHandler`（prefetch 50 起步压测调至 200–500；**多行 VALUES/COPY 批量写**每批 500 条或 100ms flush；Redis `device:latest:{deviceId}` 更新并行拆分）；`AlertHandler` 独立消费者（阈值→iot_alerts→Redis pub）；`iot_raw_data` 纳入 pg_partman 按天分区。
20. 设备/传感器/告警/采集任务 REST（4.7 节 18 接口）。
21. **WebSocket 链路 → 大屏**（严格先 WS 后大屏，避免假数据联调）：`WsBroadcastManager` 按频道订阅（`ws:broadcast:{channel}` 订阅/发布同名）+ 频道级 1–5Hz 合并推送 + 慢连接降级；`hms-dashboard` Vue3 订阅 production.realtime / device.status / alert 三频道。
22. 质量域（4.8 节 7 接口）：检验标准/检验记录/缺陷处置。
23. ERP/WMS 集成：WireMock 桩先行；`IntegrationService` + `CircuitBreaker`（成功重置计数版）+ Saga 编排 + 同步日志重试。

### M2 出口标准
- 模拟器 1 万条数据全量入库；故意投毒消息 3 次重试后进 DLQ（有界重试验证）；
- 大屏实时刷新延迟 < 2s，告警→WS→看板弹窗全链路演示通过；
- k6 复合门禁：入库 20k msg/s + 1000 WS 连接 + REST 混合三者同跑 30 分钟，REST P95 劣化 < 30%、消费 lag P99 < 5s。

## 阶段 M3：高可用与容量验证（第 15–18 周）

24. 生产 compose：backend replicas≥2、Redis Cluster 3 主 3 从（clusterMode=true）、RMQ 3 节点 quorum/镜像队列、Nginx TLS+WSS。
25. **PgBouncer transaction 模式切换**（切换前全量 SQL 会话无关审查 + 灰度单实例先行）；读写分离（历史/审计/列表走只读副本）。
26. 无状态扩容验证：JWT 黑名单/会话/权限全走 Redis；outbox 投递器多实例无重复投递；WS 跨实例广播双实例实测；IoT 3 副本按 `ceil(设备数/5000)` 验证。
27. **容量总验收**：k6 全链路 2 小时（万级模拟设备 20k msg/s + 千级 WS + 管理端 5k QPS），PG/Redis/MQ 无积压、DLQ 增量≈0、分区巡检通过；不达标禁止 GA。
28. 可观测性：Prometheus 指标（QPS/延迟/MQ lag/outbox 待投递/广播扇出/分区剩余天数）+ 告警；看板降级策略（IoT 宕机展示历史数据）。
29. 发布演练：Nginx 蓝绿（新版 10% 流量）+ expand/contract 回滚演练 + kill 实例 30s 自愈验证。

## 依赖关系

```

              hms-web 骨架与 A 域 API 并行
M1 → MQ拓扑(17) → IoT采集(18) → 入库(19) → 设备API(20)
     质量(22)、集成(23) 可与 18-20 并行（不同人员）
     WS链路(21) → 大屏(21)
M2 出口 → PgBouncer(25)/Cluster(24) 并行 → 扩容验证(26) → 容量验收(27)

```
关键串行链：**迁移脚本 → 认证中间件 → 报工事务（outbox 首个使用者）→ M1 验收**；大屏严格后置于 WS 链路。

## 测试计划

- 单测（GTest）：报工状态机与并发超报、data_scope 5 档 SQL 生成、JWT 黑名单、熔断器计数语义；
- 集成测试：docker-compose 起测试库；migrate 往返 + 跨分区插入；MQ 契约测试（schema 校验每 PR）；
- E2E：M1 `m1_flow.sh` 全链路脚本；M2 大屏链路演示脚本；
- 压测：`perf/k6/` 三套脚本作为阶段出口硬门禁。

## 风险与缓解

| 风险 | 缓解 |
|------|------|
| Drogon C++ 生态（AMQP/ORM）踩坑 | S0.1 前置一周消化并锁版本；rabbitmq-c 备选 SimpleAmqpClient |
| AuthForge 不兼容 | 3 天限时 spike + Go/No-Go；默认自研薄层不阻塞主线 |
| 分区缺失致审计/入库写入失败 | S0.2 定制镜像；partman premake 预热；CI/部署期分区断言；M3 监控告警 |
| fail-closed 漏注册致新接口 403 | CI 权限映射门禁 + perm_routes.cc 集中维护 |
| MQ 契约双端漂移 | contracts/ 单一事实源 + schema 契约测试每 PR |
| Drogon 回调地狱 | 协程写 Service、回调留底层的强制约定 |
| 事务前发 MQ 回潮 | 全项目只允许 OutboxService.enqueue() 一个入口，grep 门禁 |
| 容量预估未经实测 | 每里程碑 k6 门禁，M3 全链路验收不达标禁 GA |

## 假设

- 团队可按阶段并行 2–4 人（前端与后端可并行）；时间盒按 18 周估算，人力变化时按比例伸缩但阶段顺序不变。
- AuthForge 结论以 S0.3 spike 实测为准；若 spike 证明嵌入式集成零成本且出现 MFA 强需求，可在 M2 决策点重议（ADR 0001 留切换预案）。
- ERP/WMS 联调依赖对方提供接口文档，M2 前以 WireMock 桩替代。

## Rejected Alternatives

1. **AuthForge 嵌入式 SDK 作为 MVP 主方案**（方案 B 主张）：拒绝——双用户主数据漂移风险、升级耦合、MVP 无 OAuth2 需求；保留为 M3 后 SSO 场景预案。
2. **AuthForge 独立授权服务先行**：拒绝——MVP 增加登录路径一跳与运维单元，收益为零。
3. **三子系统并行大爆炸开发**：拒绝——MQ 契约/WS 链路未冻结前做看板必然返工；改为"垂直薄切片逐层加厚"。
4. **压测放到 M3 才做**：拒绝——批量入库、分区、扇出等设计需要 M2 即实测背书，否则容量风险全部积压到上线前。
5. **Flyway/手工 SQL 管理迁移**：拒绝——选 golang-migrate（纯 SQL、语言无关、CI 往返测试友好）。
